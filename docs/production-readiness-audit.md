# SomaCare — Production & Launch Readiness Audit

Date: 2026-08-15. Method: static codebase scan + live-server verification. Scope: everything needed before the site is published and spread.

Legend: 🔴 Blocker (launch-critical) · 🟠 High (should ship with v1) · 🟡 Medium · 🟢 Low/polish

---

## 🔴 Blockers — fix before publishing

### B1. No password reset
There is no `/reset-password` route, no "forgot password" link on `/auth`, and no `resetPasswordForEmail` call anywhere. Users who forget their password are permanently locked out. Supabase email auth makes this easy (`resetPasswordForEmail` + a public recovery route that calls `updateUser`), it just doesn't exist yet.

### B2. Zero public/SEO surface — nothing to "spread"
The landing page was removed (requested), so `/` redirects to `/auth` — and `/auth` is `noindex`. Result:
- No page on the site is indexable by Google (no robots.txt, no sitemap.xml, no public content).
- No `og:image` anywhere (root head has `og:title`/`og:description` but no image), so social shares render as bare links.
- The site has no URL that can be linked in a bio, ad, or press release.
For "publish and spread" this needs a deliberate answer: either a minimal public page (value proposition + sign-up CTA + og image), or robots/sitemap/meta on whatever public pages exist (e.g. `/auth` at minimum can host the og tags). This was flagged as a consequence of the landing removal.

### B3. Store checkout is a demo, not commerce
`/store` checkout button shows a toast: `"Order placed — demo checkout"`. Products come from a static `src/lib/store-catalog.ts` (no `products`/`orders`/`cart_items` tables), no Stripe/Paystack/Flutterwave, no order tracking, no receipts. If the store is in the launch scope this is a blocker; otherwise it should be hidden or clearly labeled "demo" — shipping a fake checkout on a health app erodes trust.

### B4. Data-rights features are disabled stubs (GDPR)
In Settings → Privacy/Account/Reports:
- **Delete account** — disabled ("not yet available")
- **Data export (CSV/JSON)** — disabled ("not yet available")
- **2FA** — disabled ("not yet available")
For a health app processing sensitive data these are close to mandatory (and the original plan lists them as hardening phase 9). Delete + export are the ones regulators and app-store review care about.

### B5. Transactional email — not integrated
Plan calls for email (verification, summaries, reminders, password reset) via Resend. There is no `RESEND_API_KEY`, no email-sending code, no email templates. Password reset (B1) and account-verification messaging depend on this. Supabase's built-in auth emails (confirmations) can be configured via the Supabase dashboard, but app-generated email (summaries, abnormal-vitals alerts — the settings UI already exposes these toggles) has zero backend behind it.

### B6. Web push / PWA / offline — not built
Notifications only work through Capacitor native local notifications. There is no web push (no VAPID keys, no service worker, no `manifest.json`), no offline support, and no "Add to Home Screen" for web users. The plan promised Workbox + Web Push. For a health app where medication reminders are a core retention loop, web users currently get nothing.

### B7. Deployment target is mid-flip-flop (uncommitted)
- `git` HEAD targets **Vercel** (`preset: "vercel"`), the working tree targets **Cloudflare** (`preset: "cloudflare-module"`).
- `.vercel/` is linked to a Vercel project; `.output/` is a Cloudflare build; `.vercel/output/` (stale) may still exist.
- `npm run deploy` works only against Cloudflare (`cd .output/server && npx wrangler deploy --config wrangler.json` — wrangler.json is generated by the build there).
- The handoff doc (2026-08-14) explicitly says this flip-flop "should be resolved deliberately" — i.e. commit the chosen target.
- **No custom domain**: live site is `https://nyansela-somacare.somalabs.workers.dev` — hard to type, hard to share, no SSL-trust branding.

## 🟠 High — should ship with v1

### H1. AI endpoints: single point of failure + no rate limiting
All 5 AI routes (`/api/chat`, `/api/fitness-suggestion`, `/api/nutrition`, `/api/sleep`, `/api/medverify`) call the same `process.env.NVIDIA_API_KEY` against `nvidia/nemotron-3.5-lightning-30b-a3b`. Gaps:
- One key = one outage; no fallback to the second key already in `.env` (`GEMINI_API_KEY`).
- **No rate limiting** on AI or auth endpoints (plan promised Cloudflare/edge counters) — token costs are unbounded and abuse-prone.
- Worker secrets must be set in Cloudflare (`wrangler secret put NVIDIA_API_KEY ...`) separately from the local `.env`.

### H2. No tests
No test script in `package.json`, no test files. For a health app, at minimum: unit tests for the server fns / health-context / theme-store, plus a post-deploy smoke check (the handoff already does manual smoke checks).

### H3. No analytics / observability
Errors hook into `window.__lovableEvents` (Lovable platform). There is no product analytics (activation, retention), no uptime monitoring, no server-side request logs. Without analytics you can't measure onboarding drop-off or know if the site is down — both essential for "spread."

### H4. No admin surface
`user_roles` + `has_role()` exist in the schema, but there is no `/admin` route or UI (plan: role-gated CRUD for users, providers, products, content). Nothing to moderate or seed content (news, providers, products) at launch.

### H5. Legal pages missing (and already linked)
`/auth` says *"By continuing you agree to our terms and privacy policy"* — **no such pages exist**. A health app needs at minimum: Privacy Policy, Terms of Service, and (for Ghana/EU users) a consent notice. The medical disclaimer is present on auth but has no dedicated page either.

### H6. Emergency SOS is a tel: link only
Plan: SOS → SMS to emergency contacts with live location. Actual: a "Call 112" button + medical ID + contact list. Fine for v1, but the plan's SMS-to-contacts behavior is unimplemented (no SMS provider — Twilio was explicitly dropped from the plan).

## 🟡 Medium

- **M1. Apple sign-in** — plan lists Google + Apple; only Google is wired (via Lovable OAuth). Apple requires an Apple Developer account + Supabase/Lovable provider config.
- **M2. i18n hygiene** — locales exist for en/tw/ee/ga, but settings marks ee/ga as "Coming Soon"; stray files (`en-new.json`, `en.json.backup`) and a harmonization report suggest drift. Decide which languages actually ship.
- **M3. Stray root files** — `index.html.bak`, `test-chat.mjs`, `ts-errors.txt` (handoff doc already flagged `test-chat.mjs` for removal).
- **M4. Rate-limit / HIBP auth hardening** — plan's HIBP leaked-password check and auth rate limiting are unimplemented.
- **M5. Audit log** — `activity_logs` table exists in schema; nothing writes to it (plan wanted login/role-change/export events logged).

## 🟢 Low / polish

- **G1. Social share polish** — og image, twitter:image, favicon variants exist but no shareable card asset.
- **G2. Gamification** — achievements tables exist in plan but not in migrations; not needed for v1.
- **G3. Voice (STT/TTS), OCR/vison** — in plan's AI layer; only text chat is built. Nice later.
- **G4. Telemedicine / calendar ICS export** — appointments exist; ICS export and WebRTC room not built.
- **G5. Barcode scanning / drug-interaction API** — medverify (AI) exists; RxNorm/OpenFDA and `@zxing/browser` not wired.

## Recommended execution order

1. **Resolve deployment** (B7): commit the Cloudflare target, set worker secrets, add a custom domain. Get a stable, reproducible deploy.
2. **Password reset** (B1) + **transactional email** (B5): these go together; they're the top user-facing blocker.
3. **Legal pages** (H5) + **privacy/cookie consent** — unblocks app-store review and GDPR.
4. **Data export + delete account** (B4) — implement on top of the existing schema (all tables are `user_id`-scoped, so export/delete are straightforward).
5. **Decide the store** (B3): build real checkout or take the store out of scope for v1.
6. **Public/SEO surface** (B2): sitemap/robots + og tags on whatever public pages exist (or a minimal public page if you want a shareable landing again).
7. **Web push / PWA** (B6) + **rate limiting on AI** (H1) before significant user growth.
8. **Analytics** (H3) + **tests** (H2) as part of the launch checklist.
